### ✉️ Draft reply to customer (ready to send)

**Subject:** Re: SSL certification process

Hi Joel,

Great to meet you, and thanks for laying out your goals. You’re right—the industry is moving to shorter‑lived public TLS certs on a phased schedule, which will increase renewal frequency. The good news is that the Azure pieces you’re already using (Key Vault + Application Gateway) are built to support automated lifecycle management so you can eliminate manual steps and outage risk.

**What's changing**  

The CA/Browser Forum approved a phased reduction of public TLS certificate lifetimes (and domain-validation reuse windows). Practically, that means planning for semiannual renewals from March 2026, quarterly from 2027, and roughly monthly by 2029—aligning with the multi-year phase-in you mentioned. Automation becomes essential.

**Recommendations**

1.  **Keep Azure Key Vault as the system of record** for all internet‑facing certs and make Application Gateway reference a *versionless* Key Vault secret ID. With that configuration, App Gateway automatically picks up the newest certificate version as soon as Key Vault has it—**eliminating the manual steps that can lead to outages** and providing true zero‑downtime certificate rotation.

2.  **Choose one of two renewal paths** (we can support both where needed):
    *   **Integrated CA auto‑renew (least friction):** Use Key Vault Certificates with an integrated CA (e.g., DigiCert or GlobalSign). Key Vault requests/renews on your policy, and App Gateway consumes the latest version automatically.
    *   **Adobe‑managed CA automation:** If you must use Adobe‑managed certs or a non‑integrated CA, wire up a small automation: Key Vault "near‑expiry" → Event Grid → Azure Function/Automation Runbook that obtains the new cert from your CA, writes a new version to Key Vault, and lets App Gateway rotate seamlessly. This automation will significantly reduce the operational cycles your team currently spends on renewals while eliminating the worry and outage risk you mentioned.

3.  **Governance & visibility**
    *   Enforce **expiry dates** on Key Vault secrets/certificates and alert well before SLA thresholds.
    *   Subscribe to **Key Vault near‑expiry events** and track renewals in a dashboard/workbook.
    *   Standardize naming/tags so each certificate clearly maps to its endpoint, environment, and owner.

4.  **Design for zero‑downtime cutover**
    *   For critical endpoints, validate the renewed certificate on a staging listener or canary before it becomes active.
    *   Document a rollback (previous version still in Key Vault) even though rotation is typically instantaneous.

**A few clarifying questions to tailor the plan**

*   Which CAs are in scope today (Adobe internal PKI, DigiCert, GlobalSign, others)?
*   Which endpoints use these certs besides Application Gateway (e.g., Azure Front Door, App Service, AKS ingress, CDN)?
*   Are your current Application Gateways v2 and configured to read a *versionless* Key Vault secret via managed identity? Any private endpoint/firewall constraints on the vault?
*   What renewal/validation windows and change‑freeze periods do your teams need us to respect?
*   Do you have a preferred alerting channel (email, Teams, ticket) and lead time for “near‑expiry” notifications?

**Proposed next step**  
If it helps, we can run a 60‑minute working session to map your certificate inventory, confirm App Gateway/Key Vault settings, and stand up a small pilot (one domain) of the automation path you prefer. From there we’ll scale the pattern.

Thanks again—happy to partner with you to take the manual work (and worry) out of renewals.

Best,

### ✉️ Short & Sweet Version

**Subject:** Re: SSL certification process - Automation recommendations


---

Hi Joel,

Thanks for the context. You’re right—public TLS cert lifetimes are trending shorter (semiannual by 2026, monthly by 2029). The good news is that your current approach (Key Vault + Application Gateway) can be fully automated to remove manual steps and outage risk.

**Recommendations**

- Keep Azure Key Vault as the source of truth and have App Gateway listeners reference a versionless Key Vault secret via managed identity—this enables seamless pickup of new cert versions.

- Renewal paths:
    - Integrated CA (e.g., DigiCert/GlobalSign): auto‑renew in Key Vault  where policy allows; App Gateway picks up new versions automatically. 
    - Adobe‑managed CA or Non-integrated CA: Key Vault near‑expiry event → Function/Automation → obtain/validate new cert → write a new version to Key Vault.

- Governance:
    - Add alerts on near‑expiry, standardize naming/tags (service/env/owner), and validate zero‑downtime rotation with a canary listener/slot.

- For other edges (e.g., Front Door/App Service/AKS Ingress), use managed certs where policy permits or the same Key Vault pattern.

This eliminates the operational cycles and worry you mentioned while future-proofing for shorter certificate lifespans.

A few quick questions to consider before we proceed:

- Which CAs are in scope today (Adobe internal, DigiCert/GlobalSign, others)?
- Any endpoints beyond App Gateway that we should include?
- Are your App Gateways v2 and already using managed identity + versionless secret references?
- Any network restrictions (private endpoints/firewalls) on the Key Vault?

Best,
